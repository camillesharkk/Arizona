# Question-bank editorial review

1. Pin the GitHub main and production deployment SHAs, verify the domain, and inventory the canonical banks and release flags. Trace read paths from free questions, full simulations, topic drills, Daily Study and Pro authorization. Compare generated public projections with the source banks. Inspect database schemas read-only to distinguish editorial content from user progress and snapshots.
2. For each state, record whether official agencies or the designated provider publish a complete exam bank, samples, an outline or just operational instructions. If a complete public bank cannot be established, describe the review as a check of this site's original questions against current official statutes, handbooks and exam instructions.
3. Open the agency notice, operative law and applicable administrative rules. Read the cited PDF pages and version. Keep signing, publication, revision, effective, access and review dates distinct. Use the enacted session law when a codification lags, and record any conflict. Queue future provisions for their applicable dates.
4. Check each stable ID against primary evidence. Read the stem, every choice, key, explanation and distractor feedback. Check jurisdiction, assumptions and exceptions. Follow related cards, guide examples, SEO articles and templates. Log the authored location, pinpoint source, timestamp, conclusion, and before/after differences.
5. Label each result verified unchanged, revised and rechecked, pending, or retired. Distinguish verified official changes, existing site errors and editorial clarifications. Record the reason for a hold. Use an existing draw-eligibility boundary to pause an unresolved question while preserving historical lookup, answer keys, attempt IDs and versioned snapshots.
6. Keep editorial review timestamps by stable ID at `data/question-review-dates.ts`. The display projects the actual timestamp to its Asia/Shanghai calendar date. Keep the former date on pending questions. The study-store `lastReviewedAt` records a learner's own review. Source-registry dates record inspection of a source. Article `updated` supplies the affected article's modification date. The full-audit date advances only when every question in the stated scope has passed.
7. Regenerate affected projections with the state publishers. Run `node --conditions=react-server scripts/source-evidence-audit.mjs [url-manifest.json] [question-inventory.jsonl]` and the state's data and grading checks. Validate clean draws and exact existing-sitting restore, archive access, cross-state isolation, trial boundaries, saved and wrong items, and guest-to-account import. Run types, build and UI acceptance through the normal entry points.
8. Confirm the audited commit at the production domain before describing the release as live. The Community Insights author must be an existing verified site team account using the normal signed-in workflow. Look for an existing thread. Use a short note for a verified rule change and keep any site-only correction visibly distinct. Include the official effective date and source, affected topics and a small number of IDs.

Keep resumable evidence and the canonical coverage checkpoint in `docs/question-bank-audit/`. Each passed row must identify the reviewed content version and SHA-256, actual review timestamp, pinpoint evidence and conclusion. Compare its fingerprint against a fresh inventory before carrying it forward. Any mismatch requires a new review. Review dates and draw holds are excluded from the content fingerprint. Save complete working notes with the private audit files and omit full stems, choices, answers and feedback from the public evidence ledger.

After regenerating the inventory, run `node scripts/question-audit-checkpoint.mjs <question-inventory.jsonl> docs/question-bank-audit/evidence.jsonl docs/question-bank-audit/checkpoint.json`. Inspect stale evidence and the per-state next pending ID. Write the subject to resume and any source conflicts in the continuation report.

Use a new version when publishing a substantive correction of the same question. Preserve the exact former question and key. If a clear replacement assesses a different rule, retire the old ID from new draws, issue a new ID, and record both directions of the relationship. Count each original once. Validate replacement evidence separately. Flag purely editorial events as silent so older versions remain readable without prompting a new review.

Run `node scripts/question-version-verify.mjs` for version resolution and receipt behavior. For browser acceptance, build locally, install Playwright in the local tools directory, then run `node scripts/question-updates-browser-verify.mjs` against that build. The script seeds its own fixtures, starts a loopback server with a local file store, and checks missed acknowledgments, cross-device deduplication, and the update list.
